## 排查：云台姿态角"停住后自动归零"问题

现象：MPU 平铺放置，转动时 pitch/roll 显示正常，但停在某个角度不动后，数值会慢慢衰减回 0。

定位（读 main.c / mpu6500.c / tim.c / steer.c 后确认）：

1. **`Calibrate_Gyro()` 完全没生效（根本原因）**
   - 声明 `void Calibrate_Gyro(float gx_bias, ...)` 是**值传递**，没有指针/引用。
   - main.c 里以未初始化变量调用 `Calibrate_Gyro(gx_bias,gy_bias,gz_bias)`，全局变量默认 0，函数内累加 2000 次样本后写的是**函数形参的副本**，调用方变量永远是 0。
   - 后果：`gx = (gyro[0]-0)/131.0f` 带着陀螺仪零偏（典型零点几到几 °/s），互补滤波里 `pitch += gx*dt` 被持续积分 → 静止时角度缓缓漂移。
   - 修法：改成 `void Calibrate_Gyro(float *gx_bias,...)` 并传 `&gx_bias`。

2. **互补滤波一次融合不够**
   - 单次 `pitch = 0.98*(pitch+gx*dt) + 0.02*acc_pitch`，每 10ms 只有 2% 权重把角度拉向加速度计解算值，加速度计那个 2% 实际**还没战胜陀螺的积分漂移**，所以回归很慢（表现为"慢慢归零"）。
   - 修法：循环融合多次（如 for k=0;k<5;k++，等效 0.9 权重）或降低 ALPHA 到 0.90~0.95。

3. **其他确认项**
   - TIM3：PSC=7199, ARR=99 → 10 kHz，即 **0.1ms 中断**，但 `dt` 写的是 0.01f（10ms），**dt 比实际小 100 倍**，导致陀螺积分项 `gx*dt` 被缩小 100 倍。tim3 需重设为 PSC=7199, ARR=9999 (10ms)，或把 dt 改成 0.001f。**这一条会让漂移变慢，但方向相反的错误掩盖不了问题，必须一并修。**
   - 姿态角变量 `pitch/roll` 被 ISR 写、main 循环读，未加 `volatile`。
   - `OledChoice()` 里 `while(HAL_GPIO_ReadPin(...))` 在 TIM3 中断里死等按键释放，是危险写法（ISR 内阻塞）。
   - CAN 帧 DLC 注释写 4 字节，实际只填了 2 字节，DLC=2。
   - 加速度计解算：`acc_pitch = atan2(accel[1], accel[2])*57.3`，roll 用 `atan2(-accel[0], accel[2])`，平铺安装下这两个公式是对的。

项目约定：软件 I2C（MPU PB10/PB11，OLED PB8/PB9）；TIM2 CH1/CH2 出 50Hz 舵机 PWM，CCR 500~2500 对应 0~180°。

## 第二轮：修完零偏后仍归零 → 用户补充关键信息

用户反馈：**面包板上不漂，把模块搬到云台上才漂**。且用户已自行把 TIM3 改回 PSC=7199/ARR=99（10ms），dt 也改回 0.01f —— 与我上轮建议一致，此条已闭环。

搬到云台新增的三个变量：
1. 两个舵机开始通电并与 MPU 机械耦合 → 震动 + 电噪声
2. 接线变长／可能靠近舵机 PWM 线 → 软件 I2C 无 ACK 校验，读错静默通过
3. 舵机浪涌电流 → 共地共电源时 5V/3.3V 跌落

三个候选机理：
- **(a) 加速度计饱和削顶**：量程只有 ±2g（ACCEL_CONFIG=0x1C 写 0x00），舵机抖动下 az 容易打满 ±32767，`atan2(ay,az)` 里分母变大 → 角度被拉向 0。一行修复：`MPU_WriteReg(0x1C,0x10)` 改 ±8g（atan2 是比值，不用改别的换算）。
- **(b) 震动导致 atan2 瞬时值翻转**：az 在 0 附近穿越时 `atan2(ay,az)` 在 ±90° 跳变，均值被拉向 0。修复：给加速度计加低通滤波。
- **(c) 供电/接线**：舵机浪涌 → MPU 掉电复位或 I2C 读错。

本轮改动（`Core/Src/main.c`，已落盘）：
- 新增全局 `volatile float acc_pitch, acc_roll;` 和 `uint8_t mpu_who;`。
- ISR 里 `acc_pitch/acc_roll` 由局部改为全局（原来是函数内局部变量，外部看不到）。
- 启动时读 `MPU_ReadReg(0x75)` 存入 `mpu_who`（正常 0x71）。
- 主循环 OLED 改为**临时调试屏**：Line1 = aP/aR（加速度计单独解算），Line2 = pitch，Line3 = roll，Line4 = WHO 十六进制 + 加速度 Z 原始值。已用注释块标明"问题解决后整段删掉"。
- `dt` 注释里的 ARR=9 更正为 ARR=99。

**决定性实验（已告知用户）**：拔掉舵机信号线 / 给舵机独立 5V 供电，再按住角度看是否还漂 —— 这是面包板与云台唯一的实质差异。另外要确认"数字归零时云台是否物理上已经回平"（舵机扛不住负载会自己掉回水平）。

## 第三轮：诊断数据回来了

用户实测：**aP / aR 一直是 0，从没动过；az 水平时约 15000+（≈1g）；WHO = 0x70。**

分析：
- `atan2(ay, az) ≈ 0` 且 `az ≈ 15000`（分母不小）→ 只能是 **`ay ≈ 0`**；`aR ≈ 0` 同理 → **`ax ≈ 0`**。
- 换算：`aP` 取整后为 0 意味着倾角 < 1°，即 `|ay| < ~260`（满量程 16384）。**重力完全没有落到 X/Y 轴上。**
- WHO=0x70 经查证是 MPU6500 的正常 ID（0x71=MPU9250，0x68=MPU6050），且 az 能读出 1g → **I2C 通信与芯片本身都正常，排除通信/供电/饱和三种猜测**（az 没打满 ±32767，饱和假说排除）。

结论方向：**传感器的 Z 轴始终与重力同向 → 相对于重力，传感器一直没被真正倾斜过。** 两种可能：
- (A) 加速度计 X/Y 通道在云台安装后异常（但面包板上正常，硬件故障可能性低）
- (B) 云台物理上让传感器保持了水平：舵机未通电/机械自由、负载重力自平衡、或用户实际只转了偏航轴

本轮改动（`Core/Src/main.c`）：调试屏改为显示**加速度三轴原始值 + 加速度计解算角**：
```
X: <±xxxxx>
Y: <±xxxxx>
Z: <±xxxxx>
aP:<±xxxx> aR:<±xxxx>
```
（`OLED_ShowSignedNum` 布局已逐列核对：X/Y/Z 用 Column=3/Length=6 占 3~9 列；aP 用 Column=4/Length=4 占 4~8，aR 用 Column=12/Length=4 占 12~16，正好 16 列不溢出。）

给出的判据：**手持模块/整个云台强迫倾斜 30°，正确的话 ax 或 ay 应到 ±16384×sin30° ≈ ±8200。** X/Y 有变化 → 加速度计正常，是云台把传感器保持水平了（非软件 bug）；X/Y 仍为 0 → 加速度计 X/Y 通道问题。pitch/roll 暂时从调试屏移除，因为症状已知、当前需要的是原始数据。

补充结论：`mpu_who` 仍保留在启动时读取（自检用），但已不再上屏。

## 第五轮：定位到真正根因 —— `math.h` 未包含，`atan2` 隐式声明

用户明确目标：**双舵机把 MPU 稳定保持水平**。再全量审查后找到真凶。

**根因**：全工程（除外设库）**没有任何地方 `#include <math.h>`**（已用 grep 确认：Drivers/STM32F1xx_HAL_Driver、Drivers/CMSIS/{Core,Device}、APP/BSP/Core 全部无匹配）。而 `Core/Src/main.c` 在 ISR 里调用 `atan2()`。Keil ARMCC5 下会给出 warning #223-D "declared implicitly" 并按 **返回 int** 处理 —— 对返回 double 的 atan2，实参与返回值都从错误的寄存器取，**结果恒为垃圾值（实测表现为恒 0）**。

**症状完美吻合**：`acc_pitch = acc_roll = 0` → 互补滤波退化为
`pitch = 0.98*(pitch + gx*dt) + 0.02*0` = **漏积分器**
→ 静止时指数衰减，τ = dt/(1-0.98) = 0.5s → 「慢慢归零」
→ 转动时 gx*dt 在驱动 → 「转动时角度看起来是对的」

这也解释了第四轮用户说的"原始数据都没问题"与"aP/aR 恒为 0"并存 —— 原始值好、是 atan2 转换坏了。**我第四轮把 aP=0 误判成"ay≈0、重力没落到 X/Y 轴"，此处更正。**

面包板正常的原因推测：当时用的是另一版代码（含 math.h），或 UB 行为随代码改动而改变。

**修复**：`main.c` 加 `#include <math.h>`。验证方法：看编译日志是否有 "declared implicitly" / warning #223-D。

**针对"保持水平"目标的其余审查发现**（按严重度）：
1. 🔴 闭环符号未验证（`ccr = Init - Kp*error`），接反即正反馈飞车
2. 🔴 只有 P（Kp=1.5, Ki=Kd=0）→ 有稳态误差，物理上不可能"始终水平"，需要 I 项 + 抗积分饱和
3. 🔴 `if(fabs(error)<1.0f) pid_out=0;` 是错的（现在被注释）—— 应保持上次输出，不是归零
4. 🔴 没有输出限速（slew rate），大误差时舵机跳变会把平台甩出去
5. 🔴 两轴独立 PID 假设不成立：双舵机云台通常是串联机构，pitch 会改变 roll 轴方向
6. 🟡 `Pitch_Base=4.0f`（控制目标）与 `Pitch_Bias=5.0f`（显示零点）不一致；目标是水平的话 Base 应为 0
7. 🟡 CAN 协议不一致：注释写"×100 保留两位小数"，代码是 `(int8_t)(pitch)`（没 ×100，量程仅 ±127°）；DLC=2 与注释"4字节"矛盾
8. 🟡 `HAL_CAN_AddTxMessage` 返回值未检查 + `AutoRetransmission=DISABLE` → 静默丢帧
9. 🟡 `steer.c` 重复定义 `PID_t`（steer.h 也有一份，steer.c 却未 include steer.h）
10. 🟡 `OledChoice()` 是死代码（主循环未调用），`key_flag` 置 1 后无处清零
11. 🟡 软件 I2C 无 ACK 检查；OLED 的软件 I2C 完全无延时（可能超 SSD1306 400kHz 规格）
12. 🟡 `Calibrate_Gyro` 启动耗时约 7s，且标定期间不能碰板子；陀螺零偏有温漂
13. 🟡 `MPU_I2C_Init` 未配 DLPF(0x1A) / 采样率(0x19)，也未校验 WHO_AM_I

本轮仅审查，**未改动任何代码**（用户只要求检查）。

## 第八轮：加 Ki 后出现"小幅度抽搐" → 积分死区 + 加速度低通 + D 项限幅

用户反馈：补上积分后动作到位了，但出现**小幅度抽搐**。

诊断（按可能性排序）：
1. **积分 + 舵机死区的极限环（最主要）**：舵机自身有 3~5µs 不灵敏区 ≈ 0.3~0.5°。误差落在死区内舵机不动，但积分仍在累加，攒够了一下窜出去 → 平台抽一下 → 静下来 → 再攒。P 项不会造成这种自激（比例项自限幅），**只有 I 项会**。这正是"加了 Ki 才出现"的原因。
2. **震动噪声经 Kp 放大**：舵机工作时平台震动调制加速度计，`ATAN2(accel)` 结果带噪，ALPHA=0.98 只能把噪声压到原来的 ~10%，Kp=2.5 放大后就是可见的抖。云台工作时加速度计受震动是物理必然。
3. **软件 I2C 坏帧打进 D 项**：读取无 ACK 校验，偶发错帧给出离谱角速度；D 项是瞬时量，会被原样放大成一次猛甩。

```c

```

选型理由（重要，避免以后改错）：
- **0x1A=0x03 的理由**：默认 0x1A=0 时陀螺/加速度带宽 250/260Hz，对 100Hz 采样远超奈奎斯特(50Hz)，舵机振动会**混叠**回 0~50Hz 低频区，软件低通根本滤不掉 —— 所以必须在传感器端做抗混叠。41/44.8Hz 是 100Hz 采样下的教科书取值。延迟 5.9ms 在环路穿越频率(几 Hz)处只有几度相移，可忽略。放宽选项是 0x02（92/99Hz，延迟 3.9ms）。
- **0x19=0x00 的理由**：让传感器(1kHz)快于我们的读取(100Hz)，保证每拍都拿到新数据。否则传感器与定时器不同步，会时而读到重复样本、时而漏样本，反而引入抖动。带宽已被 DLPF 限住，更新快不会带噪声。

**保留了软件 `ACC_LPF_K = 0.15f`**：加速度路径的时间常数由互补滤波的 0.5s 主导（α=0.98），软件预滤波再加 ~0.06s 几乎无影响，所以没必要为了降延迟放宽它，留着多一层抗噪。

**如果还抖的下一步旋钮**（按优先级）：`ALPHA` 0.98 → 0.99（更信陀螺）、`ACC_LPF_K` 0.15 → 0.08、`DLPF` 0x03 → 0x05（陀螺 10Hz / 加速度 10.2Hz，但延迟 17.85ms 会明显变肉）。

**建议但未做**：`PWR_MGMT_1 (0x6B)` 由 `0x00`（内部 8MHz 振荡器）改为 `0x01`（PLL 以 X 轴陀螺为参考）。内部振荡器随温度漂，会直接影响陀螺零偏稳定性。因为用户当前问题是抖动不是漂移，且改时钟源会改变标定行为，故未动，仅建议。
